# Publishing

Two repositories. This one, the development repository, holds everything:
the code, `docs/`, and the records that stay private. The public
repository, `github.com/jbr/structural-lsp`, is generated from it:
`scripts/publish` filters `main`'s whole history with
[josh](https://josh-project.dev), removing the private paths from every
commit, and pushes the result to the public `main`. A commit that touched
only private paths has no public counterpart; every other commit keeps its
author, dates and message, without the private files.

`josh-filter` comes from josh's repository, not crates.io:

```sh
cargo +stable install --locked --git https://github.com/josh-project/josh --tag r26.08.28 josh-cli --bin josh-filter
```

`+stable` matters when the default toolchain is nightly: josh's
`allocative` dependency adds an `impl Allocative for !` on nightly, which
conflicts with its `Infallible` impl now that `Infallible` is `!`, and
`cargo install` does not read josh's own `rust-toolchain.toml`.

`.github/workflows/publish.yml` runs `scripts/publish` on every push to
`main` of the development repository, `jbr/structural-lsp-private`, so a
push there is a publish. It pushes with a deploy key that can write to the
public repository and nothing else; a push made with a deploy key starts
the public repository's workflows, where one made with a workflow's own
`GITHUB_TOKEN` would not. Every other workflow skips the development
repository, so CI and releases run once, on the public side. Sync runs one
way only: nothing carries a public commit back here unattended.

`scripts/publish` also runs by hand, with the same checks.
`scripts/publish --dry-run` filters and checks without pushing. A publish
fails before pushing when any commit of the filtered history still holds a
private path, or when the public `main` is not an ancestor of the filtered
history.

## What stays private

The filter in `scripts/publish` is the list:

- `journal/` and `backlog/` — session memory and planned work. Keeping them
  in this repository is what lets a backlog deletion land in the same commit
  as the code that resolves it.
- `efference.toml` — the local agent configuration for this repository.
- `reference/servers-list/` — the editor inventories as extracted, copies
  of other projects' configuration. Removed from the tree; still in this
  repository's history, so the filter removes it from every commit.
  What the catalogue reads from it is `tests/conformance/consensus.json`,
  and its analysis is `reference/editor-inventories.md`.

Adding a path to the list rewrites every public commit that contained it,
so the next publish is not a fast-forward and the push is refused. Add one
before it is first published, or accept a force push of the public
repository.

## What follows from filtering

- **Each publish is a fast-forward.** Filtering is deterministic: the same
  history filtered again yields the same commits, so a publish adds commits
  on top of what was published before. A push that is refused means the
  public repository has a commit this one does not; the script never
  force-pushes.
- **Commit hashes differ between the repositories.** A hash cited in a file
  — the conformance scores' `structural_revision` — names a development
  commit.
- **Links into private paths do not resolve publicly.** `docs/` and
  `CLAUDE.md` link into `journal/` and `backlog/`; in the public repository
  those links are dead.
- **Commit messages are published as written.**

## A contribution from outside

A pull request against the public repository is applied here — its patch
applies as-is, since every path it can touch is the same in both — and
reaches the public repository through the next publish. The pull request is
then closed with a link to the published commit. Nothing is merged on the
public side: a commit there that this repository lacks makes the next
publish fail.

## Releasing

The version bump and its `CHANGELOG.md` entry are a commit here. After
`scripts/publish`, two workflows on the public repository finish the
release:

1. `release-plz.yml` runs `release-plz release`, which publishes to
   crates.io any version not already there, pushes its tag, and opens a
   draft GitHub release whose body is the changelog entry
   (`release-plz.toml`). It never runs `release-pr`, which would commit on
   the public side. The tag is pushed with a GitHub App token: a tag pushed
   with the workflow's own `GITHUB_TOKEN` starts no other workflow.
2. `release.yml`, generated by [dist](https://axodotdev.github.io/cargo-dist/)
   from `dist-workspace.toml`, runs on that tag: it builds
   `structural-lsp` for macOS and Linux on x86_64 and aarch64 with the
   `dist` profile (fat LTO), uploads the archives and a shell installer to
   the draft, and publishes it. Regenerate it with `dist generate` after
   changing `dist-workspace.toml`; `dist plan` fails while it is stale.

The development binaries under `src/bin/` stay out of both: `Cargo.toml`'s
`exclude` keeps them out of the crates.io package, so `cargo install
structural-lsp` installs one program, and `[dist.binaries]` keeps them out
of the archives. Windows is not a target: process groups and signal
handling are unix-specific, and the non-unix front end has never been
built.

## One-time setup

In the development repository:

- **Deploy key:** generate a key pair
  (`ssh-keygen -t ed25519 -N "" -C structural-lsp-publish -f publish_key`),
  add `publish_key.pub` to the public repository under Settings → Deploy
  keys with write access, and store `publish_key` as the
  `PUBLIC_DEPLOY_KEY` secret here.

In the public repository:


- **Codecov:** add the repository on codecov.io and set the `CODECOV_TOKEN`
  secret.
- **crates.io trusted publishing:** add a trusted publisher for
  `release-plz.yml` with environment `release`, and create a `release`
  environment under Settings → Environments.
- **GitHub App:** `release-plz.yml` mints its token from the
  `structural-lsp-release` App (`APP_ID` and `APP_PRIVATE_KEY` secrets).
  Recreating it: at github.com/settings/apps/new set a name and homepage,
  untick the webhook's Active box, give Repository permissions → Contents
  read and write, and install only on this account; generate a private key
  (Credentials → Key pairs), which must exist before the App can be
  installed; store the App ID and the key as the two secrets
  (`gh secret set APP_PRIVATE_KEY -R jbr/structural-lsp < key.pem`); then
  Install App → only `jbr/structural-lsp`, never the development
  repository.
- **No Renovate:** a dependency pull request on the public side is an
  outside contribution like any other. Dependency updates are made here.
